# What this fork changes

A fork of [`leonovk/wg-rest-api`](https://github.com/leonovk/wg-rest-api) with one behavioural
change: **the client supplies its own public key, and the server never generates or stores a private
key for it.**

Upstream generates the keypair server-side at create time and returns the private key in the HTTP
response. That inverts WireGuard's trust model — a key that should only ever exist on the client is
created on the server, sent over the network, and kept in `wg0.json`. This fork removes that.

Everything else follows from it, including a guard that turns out to be necessary once the public key
becomes caller-supplied rather than server-generated.

This document is written to be readable without knowing Ruby. It describes the two commits on
`client-supplied-public-key`.

---

## The contract change

This is what a caller sees. It is a **breaking change** — an existing client that expects a private
key back will not work.

### Creating a client

`POST /api/clients` now **requires** a `public_key` in the request body:

```json
{ "public_key": "1vA80g/qHKbcio0G6ltm7u80+FSCVdZnQ7fDA23tZ1o=" }
```

| | Upstream | This fork |
|---|---|---|
| Request body | anything (stored in `data`) | must carry a valid `public_key` |
| Server generates a keypair | yes | no |
| Response contains `private_key` | yes | **no** |
| Peer's public key | the server's | exactly the one you sent |
| Missing or malformed `public_key` | ignored, key generated anyway | `400` |

Anything else in the body still lands in `data`, minus `public_key` itself.

### Updating a client

`PATCH /api/clients/:id` still accepts `public_key`, `private_key` and `preshared_key`, but now
**rejects values that are not real WireGuard keys** with `400`. Upstream accepted any string.

### Reading a client

`GET /api/clients` and `GET /api/clients/:id` omit `private_key` entirely when there is none, rather
than returning `"private_key": null`. Peers created before this change keep reporting theirs, so
existing data is not orphaned.

> `GET /api/clients/:id?format=conf` and `?format=qr` build a complete client config, which needs a
> private key. For peers created under this fork there is no longer one, so those two endpoints now
> produce a config with an empty `PrivateKey` line. That is inherent: the whole point is that the
> server does not have it. Clients that generate their own key do not need these endpoints.

## The changes

### 1. Stop generating a keypair; use the one supplied

`lib/wire_guard/client_config_builder.rb` — the class that builds a new peer's record.

Upstream ran `wg genkey` on every create and derived the public key from it:

```ruby
private_key: wg_genkey,
public_key: KeyGenerator.wg_pubkey(wg_genkey),
```

Both lines are gone. The record now takes the caller's key and has no private key field at all:

```ruby
public_key: params['public_key'],
```

`wg genkey` is no longer called anywhere in the create path. There is no fallback: a request without
a usable public key is refused rather than served with a server-generated one. Keeping a fallback
would leave the exact weakness this fork exists to remove reachable in production.

The preshared key is still generated by the server. A preshared key is symmetric — whoever generates
it, it has to cross the network once — so moving it changes which direction it travels, not whether
it is exposed.

### 2. Refuse anything that is not a real key

`lib/wire_guard/key_generator.rb` gains one constant and one method:

```ruby
KEY_FORMAT = %r{\A[A-Za-z0-9+/]{42}[AEIMQUYcgkosw048]=\z}

def valid_key?(key)
  key.is_a?(String) && key.match?(KEY_FORMAT)
end
```

That pattern matches exactly a base64-encoded 32-byte value — the shape of every WireGuard key. The
43rd character is restricted because only 16 of the 64 base64 characters can legally end a 32-byte
encoding; the rest would decode to a different length.

**`\A` and `\z` are the important part, and they are not interchangeable with `^` and `$`.** In Ruby,
`^` and `$` match the start and end of a *line*, not of the string. With `^...$` the value

```
1vA80g/qHKbcio0G6ltm7u80+FSCVdZnQ7fDA23tZ1o=
AllowedIPs = 0.0.0.0/0, ::/0
```

passes validation, because its *first line* is a valid key. `\A` and `\z` anchor to the whole string,
so it does not.

This is not hypothetical. `lib/wire_guard/server_config_updater.rb` writes each peer into `wg0.conf`
by string interpolation:

```ruby
PublicKey = #{config['public_key']}
```

That is safe while the server generates the key. Once the caller supplies it, a value containing a
newline writes extra lines into the file WireGuard reads. An injected `AllowedIPs = 0.0.0.0/0` grants
that peer full cryptokey routing — enough to spoof and receive any other client's tunnel address. A
whole second `[Peer]` block is equally possible.

The spec suite contains the reversal of this: switching the anchors to `^`/`$` makes four tests fail.

### 3. Apply the check on every path that writes a key

Validating on create is not enough. `PATCH /api/clients/:id` reaches the same `wg0.conf` through a
different route, and upstream's schema accepts key material as bare strings:

```ruby
'public_key' => { 'type' => 'string' }
```

So the create-path check could be sidestepped by updating a peer instead of creating one. Reproduced
against a running node before fixing: the request returned `200` and the injected line appeared in
`wg0.conf`.

`app/api/clients/validator.rb` now checks `private_key`, `public_key` and `preshared_key` against the
same `valid_key?`. The check is written in Ruby rather than as a JSON Schema `pattern` because the
`json-schema` gem's patterns are unanchored — the same trap as `^`/`$`, one layer up.

### 4. Guard the file itself, not just the doors to it

`lib/wire_guard/server_config_updater.rb` refuses to write `wg0.conf` at all if any value heading
into it contains a newline:

```ruby
PEER_FIELDS.each do |field|
  raise Errors::InvalidKeyMaterialError if config[field].to_s.match?(/[\r\n]/)
end
```

This is unreachable while every write path validates its input — which is the point. Two separate
routes to this file already existed and only one was guarded; the third one someone adds later will
be guarded whether or not they remember to be. Its spec exercises it by poisoning the stored config
directly.

### 5. Report errors as `400`, not `500`

`app.rb` rescues the two new error types on their routes, so a bad request gets a `400` with a
message rather than an unhandled exception. This follows the same pattern as the existing
`ConfigNotFoundError` rescues.

### 6. Omit `private_key` instead of returning null

`app/api/clients/serializer.rb` drops the field from the response when the peer has no private key,
rather than emitting `"private_key": null`. A response for a client-generated peer then carries no
such field at all.

## What is not changed

- Address allocation, the connection limit, and the `last_id` bookkeeping.
- Preshared key generation.
- The server's own keypair, which still lives in `wg0.json` as it must.
- Webhooks, stats, QR codes, the `/server` endpoint, authentication.
- Peers created before this change: they keep their stored private key and keep reporting it.

## Standards followed

The project's own, not an imported set:

- `rubocop` passes with the repo's configuration — 55 files, no offences.
- `rspec` passes: **148 examples, 0 failures** (upstream has 99; the additions are the new rejection
  cases and the config-writer guard).
- New error classes follow the existing `Errors::` pattern — one class, one fixed `message`.
- Specs follow the existing style (`subject`, `let`, `context`).
- Comments use the repo's `# NOTE:` convention.

One deliberate deviation: `KEY_FORMAT` lives on `KeyGenerator` rather than next to its first use, so
that both write paths share one definition. Having the check in only one place is the bug that
section 3 describes.

Specs that used `'a'`, `'b'` and `'c'` as placeholder keys now use real ones, since those
placeholders are no longer valid key material.

## Rebasing on upstream

The patch touches six production files. None is restructured — each change is an edit inside an
existing method, or a new file alongside existing ones — so a rebase is expected to be mechanical.

| File | Change |
|---|---|
| `lib/wire_guard/client_config_builder.rb` | two lines removed from the built record, validation added |
| `lib/wire_guard/key_generator.rb` | one constant, one method added |
| `app/api/clients/validator.rb` | one method added, called from `validate!` |
| `lib/wire_guard/server_config_updater.rb` | one guard added to `build_client` |
| `app/api/clients/serializer.rb` | one field moved behind a helper |
| `app.rb` | two `rescue` clauses |
| `app/errors/invalid_public_key_error.rb` | new |
| `app/errors/invalid_key_material_error.rb` | new |

Run `bundle exec rspec` and `bundle exec rubocop` after any rebase. The suite covers the rejection
behaviour directly, so a rebase that silently drops the validation will fail rather than pass.

## Upstreaming

**This patch is probably not upstreamable as it stands, and that is a property of the change rather
than of anyone's willingness to review it.**

Upstream is "WireGuard Easy REST API", for managing a WireGuard server: create a client, then hand
its configuration to a person. `GET /api/clients/:id?format=conf` and `?format=qr` are documented
features built on exactly that, and both need the server to hold the client's private key. Making
`public_key` required does not extend that product — it breaks a headline feature of it.

A version upstream could take would make `public_key` **optional**: use it when supplied, generate a
keypair as before when it is not. That keeps the QR and conf flows intact for everyone else.

That is deliberately not what this fork does. Leaving a "generate one for me" path reachable would
preserve the exact weakness the fork exists to remove, for a product where a server-held private key
is the thing being fixed. Both designs are correct for their own purpose, and they are not the same
patch.

The practical consequence: **this fork should be planned as permanent.** Keep the patch narrow, keep
the suite green, and expect to rebase rather than to retire it. Offering the optional-key variant
upstream separately remains worthwhile — it would benefit other people with the same requirement —
but it would be new work, not a submission of this branch.
